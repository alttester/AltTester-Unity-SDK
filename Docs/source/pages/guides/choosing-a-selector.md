# Choosing a selector

Every find and wait command takes a `By` strategy and a value. All seven strategies work; they do
not survive change equally well. The strategy you pick is the main thing determining whether your
suite still passes after an artist reorganises a prefab.

The short version: **prefer `By.NAME` for most objects, `By.COMPONENT` when a name is ambiguous or
generated, and `By.PATH` only when position in the hierarchy is genuinely what you mean.**

## The strategies, ranked by how well they survive change

```eval_rst
.. list-table::
   :widths: 18 24 58
   :header-rows: 1

   * - Strategy
     - Use it when
     - Breaks when
   * - ``By.NAME``
     - The object has a stable, meaningful name. This is the default and the right answer most of
       the time.
     - Someone renames the object, or several objects share the name. Names are not unique —
       ``FindObject`` returns the first match.
   * - ``By.COMPONENT``
     - The name is generated, localised or duplicated, but the object carries a distinctive
       script.
     - The component is renamed, moved to another assembly, or added to more objects.
   * - ``By.TAG`` / ``By.LAYER``
     - The project already uses tags or layers deliberately and you want *any* member of that
       group.
     - Tags and layers get reused. These usually match many objects; pair them with another
       filter.
   * - ``By.TEXT``
     - You genuinely mean "the thing the player sees saying X" — and the app is not localised.
     - The copy changes, or the test runs in another language. Avoid in localised builds.
   * - ``By.PATH``
     - Position in the hierarchy is the identity — "the third slot in this inventory grid".
     - Anyone reparents, wraps in a new container, or reorders. The most fragile strategy, and the
       most common cause of a suite breaking after a refactor.
   * - ``By.ID``
     - You already hold an id from a previous find, within the same run.
     - See below — it depends entirely on *which* id.
```

## The `By.ID` trap

`By.ID` matches against two different things, and they behave very differently:

- **`AltId`** is generated by AltTester® Unity SDK for objects that are present in the scene
  before the app is built. It is assigned ahead of the build, so the same object carries the same
  `AltId` on every run. This is the one you can write into a test.
- **`InstanceId`** is Unity's own runtime instance identifier. It is assigned when the object is
  created and is not meaningful across runs.

```eval_rst
.. important::
    An ``InstanceId`` copied out of the Inspector will work in the session you copied it from and
    fail in every later run. If you hardcode an id in a test, make sure it is the ``AltId``.
```

Objects spawned at runtime have no pre-assigned `AltId`, so they cannot be addressed by a
hardcoded id at all. Find them by name or component, or from their parent.

## Narrowing without `By.PATH`

`By.PATH` is tempting because it can express anything. Most of the time, what you actually want is
a search scoped to a parent — and `FindObjectFromObject` does that without encoding the whole
hierarchy into a string:

```eval_rst
.. tabs::

    .. group-tab:: C#

        .. code-block:: c#

            // Fragile: breaks if anyone wraps the list in a new container.
            var item = altDriver.FindObject(By.PATH, "//Canvas/Inventory/Grid/Slot[2]/Item");

            // Resilient: only the two names have to stay put.
            var grid = altDriver.FindObject(By.NAME, "InventoryGrid");
            var item = grid.FindObjectFromObject(By.NAME, "Item");

    .. group-tab:: Python

        .. code-block:: python

            # Fragile
            item = alt_driver.find_object(By.PATH, "//Canvas/Inventory/Grid/Slot[2]/Item")

            # Resilient
            grid = alt_driver.find_object(By.NAME, "InventoryGrid")
            item = grid.find_object_from_object(By.NAME, "Item")
```

When you do need `By.PATH`, keep it as short as it can be. `//Grid/Item` is far more durable than
a path anchored at the root, because `//` matches at any depth.

The full path syntax — including `..`, `*`, indexers and attribute selectors such as `@tag` and
`@text` — is in [BY-Selector](commands.html#by-selector).

## Selectors and inactive objects

Find and wait commands take an `enabled` parameter that defaults to matching only objects **active
in the hierarchy**. A correct selector will still find nothing if an ancestor is inactive.

Before rewriting a selector that stopped working, open the Inspector and check the parent chain.
This is a much more common cause than a wrong selector, and changing the selector cannot fix it.

## Picking selectors with the Inspector

Do not guess selectors. AltTester® Desktop shows you, for any selected object, its name, its
`AltId`, its path, and every component with its assembly — which is exactly the set of values the
strategies above take.

The recommended loop is: find the object in the Inspector, read the value you want off **Element
Details**, and paste it into the test. See
`Debugging a failing test <https://alttester.com/docs/desktop/latest/pages/guides/debugging.html>`_ for using the same view when a selector fails.

## A house style worth adopting

If you are starting a suite, these three conventions prevent most selector churn:

1. **Name the objects your tests touch, deliberately.** A test-facing name is an interface. Agree
   with the developers which objects have stable names, the way a web team agrees on `data-testid`.
2. **Keep selectors out of test bodies.** Put them in one place per screen — a page object — so a
   rename is one edit rather than forty.
3. **Never paste an `InstanceId`.** If a selector contains a long number, it is almost certainly
   wrong.
